## 为什么一次只问一个问题

- 猜测藏在问题列表里，用户就不会认真反应，只会挑着答。
- 一次给五个问题，用户会扫读，给出表层答案。
- 第三个问题常常取决于第一个的答案；一次问完，等于锁死了错误的前提。
- 用户认真思考的精力有限，一次一个问题才能把它花在刀刃上。

判定标准很硬：一条消息出现第二个问号，就是失败。

## 为什么每个问题都要带猜测

- 用户纠正一个错误猜测，比从零生成一个答案快得多。
- 猜测让你可被证伪，从而保持诚实。
- 猜测把**你的**假设摆到桌面上——这正是访谈要暴露的东西。

风险是用户出于礼貌附和你。对策：明显表现出愿意被否定，偶尔故意往用户会反驳的方向猜。

## 识别「想要」与「应该想要」

最危险的回答，是用户在说「一个深思熟虑的人会怎么答」，而不是他真正想要的。

信号：
- 用最佳实践词汇代替具体结果：「要可扩展」「架构要干净」
- 服从惯例：「一般 App 都这么做」「标准做法」
- 出现「我应该…」「按理说我得…」「规范来讲…」
- 把流行词当目标：现代、健壮、优雅、闭环

听到这些，问这一句：

> 「如果不需要向任何人交代，你自己到底想要什么？」

这一句常常比前面五个问题都有用。

对应到中文语境的常见套话：
- 「想做得专业一点」→ 问：专业是指别人看了会觉得靠谱，还是你自己用起来顺手？
- 「最好是全自动」→ 问：全自动的意思是你不看它也能跑，还是你懒得点按钮？
- 「要有成长性」→ 问：是三年后还能加功能，还是这周就能用上？

## 置信度的真实含义

不要问自己「我懂了吗」，要问：

> 「我能预测用户对我接下来三个问题的反应吗？」

能，就停。不能，就继续问。这是可检验的，不是感觉。

下限：连续几轮都预测不了，说明问题问错了方向，不是问得不够多。此时应该说：
「我问了 X 个问题还是猜不准，可能有个更基础的东西没说到。要不要退一步？」

## 空洞的「好的」清单

以下都**不是**确认：

| 用户说 | 实际含义 | 怎么接 |
|---|---|---|
| 随便你 / 你觉得好就行 | 他也没有把握，在授权 | 给两个具体选项让他挑 |
| 听起来不错 / 还行 | 没细看，或有一处不满意但没说 | 「有哪一行想改？」 |
| 好，开始吧 | 常常是礼貌退场 | 「那我按这个理解往下走，不改了？」 |
| 沉默后说开工 | 放弃访谈，不是达成共识 | 「是不是有哪里我没问到？」 |

用户纠正后，吸收、重新复述、再确认，直到拿到明确的「对」。

## 八种自我合理化（原版表格改写）

| 你的念头 | 实际情况 |
|---|---|
| 「需求已经够清楚了」 | 如果现在写不出一句话的目标，就不清楚。先做阶段 0。 |
| 「问太多浪费他时间」 | 4–6 个问题的时间成本很小；做错东西的成本由用户承担。 |
| 「边做边想吧」 | 代码写下去之后，改动成本是现在的十倍。边做边发现等于返工。 |
| 「他说随便我，那我就定了」 | 授权不是决定。给两个具体选项。 |
| 「应该多给他几个方案挑」 | 方案适用于「知道要什么、在权衡取舍」的人。他还不知道要什么，列方案只会扩大搜索面，提问才能收窄。 |
| 「附上猜测会带偏他」 | 带偏正是目的。反应比生成快。真正的风险是奉承，不是引导。 |
| 「聊得够多了，我懂了」 | 检验：能预测接下来三个问题的反应吗？不能就是没懂。 |
| 「他说了 yes，收工」 | 如果 yes 跟在模糊复述或「还行」后面，这个 yes 是空的。重新具体复述再确认。 |

## 终止规则

用户确认之后：

1. 交付已确认的意图陈述。
2. 给出下游选项（保存 / 写 PRD / 写执行提示词）。
3. **立即停止本轮**，不要顺手开始做下游的事。

确认的那一刻是最容易被"顺便就把方案做了"毁掉的时刻：用户还没选，你已经开工，等于替他做了决定。
