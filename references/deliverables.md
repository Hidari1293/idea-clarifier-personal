# 交付物模板

四份模板：意图总结（必做）、PRD（按需）、Agent 执行提示词（按需）、进度文件（可恢复）。

通用质量红线，写任何一份之前先看：

1. 每条需求都能标出来源：`[A]` 已确认 / `[B]` 建议待确认 / `[C]` 未决。没有标签的需求视为违规。
2. `[B]` 必须集中放在「待确认的建议」一节，或逐条带「（建议，待确认）」。绝不允许混进功能清单当既定事实。
3. 验收标准必须能用「是 / 否」判断。写「界面要友好」是废话，写「打开后 3 秒内能看到今天要复习的内容，不需要登录」才可验收。
4. 非目标至少 2 条。一条都没有，说明访谈里没问「不做什么」。
5. 长度跟复杂度走。简单想法写 1 页就够，凑字数会稀释重点。
6. 意图总结里不出现技术词。PRD 和提示词里才允许出现。

---

## 一、意图总结（intent.md）

给用户本人看的，不是给工程师看的。全大白话，能读出声。

```markdown
# <项目名>：我想要什么

> 访谈日期：YYYY-MM-DD｜状态：已确认 / 部分待确认

## 一句话
<我想让 ____ 能 ____。>

## 我到底想做什么
<3–5 句。用第一人称，说清做完之后哪件事变简单了。不要写功能清单。>

## 为什么现在想做
<触发它的那件具体的事。如果只是"一直想做"，就写一直想做，别编理由。>

## 想解决的问题
<现在的做法哪里不行。写具体的那一步，不写"效率低"。>

## 谁会使用
<只有我 / 还有谁。别人的话，他们懂不懂技术、会不会愿意学。>

## 典型使用场景
<一个具体片段：什么时候、在哪、手上在干什么、用它做了什么、用完什么感觉。
 写得出来一个就够，写不出两个以上说明还没想清楚。>

## 我最在意的体验
<一个词或一句话，加一句为什么。例：不要有压力——被提醒做题的App我三天就删了。>

## 我不希望出现的东西
- <明确不做 / 不要有 / 受不了的>
- <至少两条>

## 还没定的事
- [C] <…>
- [C] <…>

## 我提过但还没确认的建议
- [B] <我（Agent）建议的，用户还没表态>
```

**精简版**（轻量档项目用，10 行以内）：

```markdown
# <项目名>
- 想做的事：<一句话>
- 为什么：<一句话>
- 谁用：<…>
- 场景：<一句话>
- 不做：<…>
- 未定：<…>
```

## 二、PRD（prd.md）

只在用户要开发软件 / 网站 / Agent / 服务时生成，且意图已经确认。

### 长度纪律

| 复杂度 | 篇幅 | 说明 |
|---|---|---|
| 简单（自用小工具） | 1 页 | 只写背景、功能、验收、非目标 |
| 标准 | 2–3 页 | 全部十节，每节短 |
| 深度（多人用/要交接） | 4–6 页 | 全部十节，交互和验收要细 |

### 模板

```markdown
# <项目名> PRD

版本：v0.1｜日期：YYYY-MM-DD｜来源：idea-clarifier-personal 访谈

## 1. 项目背景
<为什么做。用户的原话可以引用。不要写行业趋势。>

## 2. 核心目标
- 目标：<一句话，可判断是否达成>
- 成功标志：<三个月后怎么知道有用>
- 不追求：<…>

## 3. 用户需求
### 已确认 [A]
- <需求> —— 依据：用户原话「…」
### 待确认的建议 [B]
- <建议> —— 我提出，用户尚未表态
### 未决 [C]
- <…>

## 4. 使用场景
### 场景 1：<名字>
- 什么时候 / 在哪 / 手上在干什么：
- 发生了什么：
- 期望的结果：
- 不希望的体验：

## 5. 功能清单
| 编号 | 功能 | 来源 | 优先级 | 说明 |
|---|---|---|---|---|
| F1 | <…> | [A] | P0 | <…> |
| F2 | <…> | [B] | P1 | 建议，待确认 |

优先级定义：P0 没有它就不能算能用；P1 明显提升体验；P2 以后再说。

## 6. 页面与交互逻辑
<按页面/界面写。每页写：进来看到什么、能做什么、做完去哪。
 不画图，用文字把"点一下之后发生什么"写清。>

## 7. 技术约束
- 运行环境：<手机 / 电脑 / 浏览器 / 只本地>
- 数据：<存哪、要不要同步、敏不敏感>
- 依赖：<能不能用外部服务、要不要账号、要不要花钱>
- 用户的技术能力：<会不会自己部署、能不能改代码>
- 时间与预算：<…>

## 8. MVP 范围
必须包含：F1、F3
可以延后：F2、F4
明确不做：<见第 10 节>

## 9. 验收标准
- [ ] <可判断真假的具体条件>
- [ ] <…>
- [ ] <用户本人试用后认为"这就是我要的">

## 10. 非目标与禁止事项
- 不做：<…>
- 不做：<…>
- 禁止：<不许擅自增加的功能 / 不许引入的复杂度>
```

## 三、Agent 执行提示词（agent-prompt.md）

目标：下游 Agent 读完就能开工，不需要再问用户已经回答过的问题。

写成可以直接粘贴的一整段（用代码块包住），开头交代身份，结尾交代边界。

```markdown
# 执行提示词：<项目名>

你是 <角色，例：一名独立开发者>。请按下面的需求完成 <交付物>。
需求已经和用户逐条确认过，不要重新做需求分析，也不要扩大范围。

## 项目目标
<一句话 + 两三句背景。说清做完之后用户能做什么。>

## 已确认的需求
1. <…>（用户明确要求）
2. <…>
3. <…>

## 功能与交互
### <功能名>
- 用户操作：<…>
- 系统反应：<…>
- 边界情况：<…>

## 技术与资源约束
- <必须 / 只能用 …>
- <不能引入 …>
- <运行在 …>
- <用户不会 / 会 自己部署>

## 优先级
P0（先做，做完就能用）：<…>
P1（P0 完成后做）：<…>
P2（有时间再说）：<…>

## 验收标准
逐条可判断：
- [ ] <…>
- [ ] <…>

## 不要擅自改动
- 不要增加 <…> 功能
- 不要改变 <已确认的交互方式>
- 不要引入 <…>（数据库 / 登录 / 第三方服务）
- 不要重命名 <…>

## 需要先问用户的事
- <确实没定、且会影响实现的问题，一条一条列>
- 除这些之外，其余都已确认，不要再问。

## 开始方式
先复述一遍你理解的目标与 P0 范围（不超过 5 行），等用户点头再动手。
```

**写好提示词的三个检验**：
1. 下游 Agent 读完还会不会问「你想要什么功能」？会，说明功能没写具体。
2. 有没有可能做多？有，说明「不要擅自改动」不够硬。
3. 验收标准能不能被别人复现？不能，说明写得太主观。

## 四、进度文件（progress.md）

用于暂停与恢复。路径 `docs/idea/<slug>/progress.md`。

```markdown
# <项目名> 访谈进度

- 更新：YYYY-MM-DD HH:MM
- 档位：轻量 / 标准 / 深度
- 当前理解度：约 __%｜还缺：<维度>

## 当前一句话理解
<一句话。恢复会话时先读这句。>

## 已确认 [A]
- <需求>（用户原话：「…」）

## 待确认建议 [B]
- <建议>（我提出，尚未表态）

## 未决 [C]
- <…>

## 已问过的问题（不要重问）
| # | 问题 | 用户回答要点 |
|---|---|---|
| 1 | <…> | <…> |

## 下一步
1. <要问的下一个问题，附我的猜测>
2. <…>

## 变更日志
- YYYY-MM-DD 从「<旧>」改为「<新>」，原因：<…>
```

**暂停时机的特殊处理**：如果用户喊停时刚好给了一条修正、而你还没确认完，把这条修正写进
`[B]` 并注明「未确认」，同时在「下一步」第 1 条写「先确认这条修正」。不要在 `[A]` 里写半成品。

**恢复时**：先读本文件 → 用两句话复述「当前一句话理解」→ 问「接着 <下一步第 1 条> 继续，还是先改 <某个 A 项>？」→ 不重问表里已有的问题。

## 五、确认话术

生成任何文件之前：

> 「我按刚才说的整理成一份 <类型>，放在 `docs/idea/<slug>/`。要现在写吗？」

生成之后：

> 「写好了：`<路径>`。哪一段跟你想的不一样，我改。」

不要一次生成四份。用户要哪份给哪份。
