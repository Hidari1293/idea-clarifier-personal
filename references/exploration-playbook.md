# 探索手册：场景模拟、方案比较、矛盾处理

用户在「不知道要什么功能」时，最没用的问法是「你想要什么功能」。
本文件提供三种把抽象变具体的工具，以及相应的中文话术。

## 一、场景模拟

### 配方

一段具体到可以"看见"的体验，由四部分组成：

```
时间/情境（用户真实生活里的） + 一个触发物 + 用户此刻的动作 + 3~4 种不同的反应方式
```

写成：

> 假设 <时间地点>，<发生了什么>。这时候你希望它 <A>、<B>、<C>，还是 <D 都不对>？

关键：选项描述的**不是功能，是那一刻的感受**。

### 示例 1：日语学习（用户已说：学过两次都断了，想利用通勤时间）

```
假设你昨天学了十个新词。今天早高峰在地铁上，你掏出手机打开它。
你希望第一屏是什么？

A. 直接开始测昨天那十个词，错了的留下来重来
B. 一篇用昨天那十个词写的小短文，读完大概看懂就行
C. 一句日语问你「昨天学的，还记得几个？」，你点一下才进复习
D. 都不是，我想要的是另一种感觉
```

用户选 B 之后，追问一句（这一步比选项本身重要）：

> 「选 B 是因为不想被考，还是因为读一篇能看懂的文章本身让你觉得有进展？」

前者说明他怕压力，后者说明他要的是「能用起来」的实感。这两个结论导出的产品完全不同。

### 示例 2：知识管理（用户已说：收藏了很多，但从来不回看）

先问现状，再模拟未来：

```
三个月后你要写点东西，正好用得上以前存过的资料。
你希望它怎么出现？

A. 你搜关键词，它把当初存的那几条摊开让你挑
B. 你不用搜，写的时候旁边冒出一句「你以前存过这条」
C. 它直接给你一页整理好的东西，你改改就能用
D. 都不是
```

### 示例 3：极其模糊的「我想做个自己的 AI 工具」

这种想法还不能直接做场景模拟，它连"什么时候用"都还没有。先问现状：

> 「最近一次你心里冒出『要是有个 AI 能帮我搞定这个』是什么时候，当时在做什么？」

拿到具体事件后再模拟：

```
假设这东西已经做好了，放在你手机上。
你用它最多的会是哪种时刻？

A. 每天固定时间打开，像上班打卡
B. 碰到具体问题才打开，用完就关
C. 一直开在旁边，想到什么就插一句
D. 说不上来，我还没想那么远
```

### 四条设计原则

1. **四个选项只在同一个维度上不同**：自动化程度、主动还是被动、形态（对话/清单/文档）、使用时机。不要两个改功能、两个改形态，那会让用户无法比较。
2. **写用户看到什么、做什么**，不写系统支持什么。「自动按遗忘曲线安排复习」是功能，「错了的词第二天还会再来找你」是体验。
3. **每个选项一句话**。写不成一句话，说明你自己还没想清楚那个体验。
4. **永远留 D「都不对」**，并且写得让用户敢选。D 被选中的信息量通常最大。

### 反模式

- 四个选项 × 三个问题 = 问卷。一次访谈里连续做三轮选择题，用户会开始敷衍。
- 选项全是功能名（导出、标签、搜索、同步）——这是让用户替你当产品经理。
- 场景和用户的生活不搭。给一个说"通勤时用"的人设计"坐在电脑前整理"的场景，等于没听。
- 把想推的方案写成 A，还描述得最详细。用户会顺着你的详细程度选。
- 在选项里预判答案（「我猜你会选 B」）。用户会顺着你的猜测选，这一题就白问了。要猜就猜维度：「我猜你更在意不用自己想起来，而不是找得全」，不指认具体选项。

## 二、方案比较

### 六个常用轴

一次只比一个轴。比较时给三样东西：用起来什么感觉、代价是什么、做起来多复杂。

| 轴 | 一端 | 另一端 | 什么时候该往左走 |
|---|---|---|---|
| 形态 | 只做一件事的小工具 | 什么都能装的平台 | 用户的问题很窄，且已经用别的东西凑合 |
| 自动化 | 它自己跑，用户不管 | 用户按一下才动 | 用户怕失控，或结果需要人判断 |
| 流程 | 固定几步走完 | 高度自由，自己搭 | 用户重复做同一件事，且步骤稳定 |
| 运行位置 | 只在自己电脑/手机上 | 云端，多设备同步 | 数据敏感、只有自己用、不想付服务器钱 |
| 节奏 | 一次做到能用 | 先能用，再慢慢加 | 用户还没想清楚，或需要尽快验证 |
| 来源 | 自己写 | 先用现成的拼 | 需求其实能被现有工具覆盖 80% |

最后一行值得特别强调：**很多时候正确答案是"别做"**。如果用户的问题用现成工具加一点习惯就能解决，直说，这比帮他做一个半成品更负责。

### 比较话术

```
这两种做法，用起来差别是这样：

走 A：<描述一天的正常使用>。好处是 <…>，代价是 <…>，做起来大概是 <一句话复杂度>。
走 B：<描述一天的正常使用>。好处是 <…>，代价是 <…>，做起来大概是 <一句话复杂度>。

我倾向 A，因为你说过「<引用用户原话>」。
但如果你更在意 <另一件事>，B 更合适。

你更怕哪个代价？
```

最后一句比「你选哪个」有效：人对损失的判断比对着收益的判断更清楚。

### 不要做的事

- 不要默认技术更先进的方案更适合。用户要的是"打开就能用"，不是"架构优雅"。
- 不要给三个以上的方案。三个以上等于没建议。
- 不要在用户还没确认「要做什么」时比较「怎么做」。

## 三、矛盾处理

用户的矛盾不是错误，是**还没排序的优先级**。四步：

1. **指出来**：「这两条会打架，我得跟你确认一下。」
2. **定位冲突点**：具体在哪一步冲突，不要抽象地说「不可能」。
3. **说清代价**：选这边，要付什么。
4. **给 2–3 条折中路径**，然后问「你更怕哪个」。

### 示例：功能要全，但必须极简、零配置

```
这两条会打架，而且冲突点很具体：在「第一次打开」和「第十次使用」这两件事上。

功能全意味着第一次打开要面对选择；零配置意味着它得猜对你的习惯。
猜对了很爽，猜错了你会觉得它碍事。

三条路：
1. 默认极简，高级功能折进二级菜单。第一次只看到三个按钮，愿意深挖的人自己能找到。
2. 两个入口共用一份数据：一个轻量版天天用，一个完整版偶尔用。
3. 砍掉大部分功能，只留你每周真的会用三次以上的那几个。这需要你先给我一份取舍清单。

你更怕哪一个：功能不够用，还是打开就头大？
```

注意没有说「这不可能」，也没有替用户砍功能。

### 其他常见矛盾

| 矛盾 | 冲突点在哪 | 通常的问法 |
|---|---|---|
| 要全自动，又要能随时改它的决定 | 自动化越深，干预点越难设计 | 你希望它在做之前问你，还是做完给你改？ |
| 要便宜，又要稳定 | 稳定来自冗余，冗余要钱 | 出问题的时候，你能接受自己修吗？ |
| 要马上能用，又要长期可扩展 | 快意味着先欠着 | 三个月内会加新功能吗？ |
| 只给自己用，又要好看 | 好看要花时间在细节上 | 好看是指自己看着舒服，还是想给别人看？ |

## 四、抽象问题 → 具体问题

| 别问 | 改问 |
|---|---|
| 你的目标是什么 | 这件事现在最烦的是哪一步 |
| 你想要什么功能 | 上次遇到这个问题时，你手上正在做什么 |
| 目标用户是谁 | 除了你，还有谁会打开它 |
| 你的痛点是什么 | 最近一次为这事烦，是什么时候 |
| 你希望什么体验 | 用完关掉它的时候，你希望自己是什么感觉 |
| 商业模式是什么 | 这东西要你自己掏钱，你还做吗 |
| 想用什么技术 | 你手上有什么能用的（电脑、手机、会不会写代码） |
| 优先级怎么排 | 这周只能做一件事，做哪件 |
| 成功标准是什么 | 三个月后，你怎么知道它有用 |
| 做过竞品分析吗 | 你试过哪些现成的，为什么不用了 |

## 五、用户答不上来：四级降级台词

同一个抽象问题只问一次。第二次必须换形式。

**第 1 级：换成具体场景**
> 「不说功能。想象明天早上你打开它，第一眼看到什么？」

**第 2 级：给三个具体例子**
> 「有人做成每天推一句话，有人做成能对话的，有人做成填空练习。哪个最像你要的？」

**第 3 级：二选一**
> 「如果只能留一个：随时能查，还是每天提醒你？选不出来也没关系，那说明两个都不重要。」

**第 4 级：我来假设，你只负责否定**
> 「那我先按 A 往下想，你觉得不对就说『不是这样』。这样比空着强，行吗？」

配套判断：
- 用户说「不知道」但立刻补了一句解释 → 他知道，只是没组织好语言，追问那句解释。
- 用户说「不知道」且沉默 → 真没想过。直接降到第 3 或第 4 级。
- 用户说「你觉得呢」→ 他在把决定权交给你。给两个选项，不要给答案。
- 用户说「都行」→ 说明这个维度对他不重要。记下来，跳过，别再问。

## 六、什么时候该收

出现以下任一信号，停止探索，进入复述：

- 能预测用户对接下来三个问题的反应
- 用户开始重复自己说过的话
- 用户回答变短、变成「嗯」「对」「都行」
- 已经问到第三个"这个重要吗"，而用户都说不太重要

继续问下去不会增加信息，只会消耗耐心。
